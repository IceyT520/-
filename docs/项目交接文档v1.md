## 1. 项目一句话与现状

北京化工大学大创项目：面向卤化物固态电解质（HSSEs）领域的 RAG 知识问答系统。
用户中文提问 → 混合检索本地文献库 → DeepSeek 严格依据片段生成带 [编号] 引用的答案。

**当前状态（2026-09）**：
- 已上线公网服务（腾讯云 2核4G Ubuntu 22.04，Gradio 网页，systemd 托管，每周 arXiv 定时追踪）
- 代码全部开源在 GitHub（仓库名暂为 `-`，建议改名）
- 核心指标：12 题 Top-3 检索召回率 100%（目标 80%），响应 1~3 秒（目标 ≤15 秒）
- 已上线功能：RAG 问答、多轮对话、引用片段核验（含页码）、参考文献导出（GB/T 7714/BibTeX）、
  问答记录下载、化学感知查询、材料对比表、性能排行榜、用户上传、知识库自生长（LLM 抽取+人工确认）、
  arXiv 每周追踪、使用指南页

## 3. 检索管线（核心，改动前先读懂）

`RAGEngine.retrieve()` 的完整链路，顺序和权重都是有血的教训换来的，**不要随意调整**：

1. 全局向量排序（MiniLM 多语言，标题拼接嵌入）权重 1.0，取 20 条
2. 化学式精确匹配分支：对问题中每个化学式 `$contains` 过滤后向量排序，权重 2.0，各取 10 条
   （向量模型分不清 Li3YCl6 / Li3ScCl6，这是召回率 33%→58% 的关键）
3. 结构化数据分支：化学式 + source=curated 双重过滤，权重 2.5，各取 3 条
   （人工校准表是事实源，单项指标查询靠它，58%→更高）
4. 三路 RRF 融合（k=60），取前 12 候选
5. bge-reranker-base 精排，**精排结果作为第三个投票者再次 RRF（权重 1.5），不是直接覆盖**
   （直接覆盖会让通用精排压制领域信号，曾导致 100%→75% 回退）
6. 同源多样性约束：每个来源最多 2 席，取最终 top_k
   （防止关键词密集的表块挤占全部席位）

显示层与检索层分离：语料和查询统一 ASCII（Li3YCl6）保证匹配；
`textfmt.prettify()` 仅在显示时转上下标（Li₃YCl₆），用显式元素表防误伤（IceyT520 不会被转换）。

## 4. 关键设计决策（以及为什么）

| 决策 | 原因 |
|---|---|
| 嵌入用 paraphrase-multilingual-MiniLM-L12-v2 而非申报书的 all-MiniLM-L6-v2 | 中文提问检索英文文献，L6 是纯英文模型 |
| 人工校准 Table 1（55 种材料，一行一材料一块） | 双栏 PDF 表格抽取必乱（曾致 LiTaOCl4 错答）；行级块保证单项查询不被同块其他材料稀释 |
| 化学式归一化为 ASCII 而非申报书说的下标 | 用户键盘输入就是 ASCII；嵌入分词更稳定；显示层再转回下标 |
| 追问先改写为独立问题（few-shot 提示词） | DeepSeek 会把上轮答案误当用户约束（"球磨法合成的…"污染查询） |
| Gradio 而非申报书写的 Jupyter | 用户选择；Notebook 仍保留在 notebooks/ 作为申报书交付物 |
| chroma 库用相对路径 + os.chdir(PROJECT_ROOT) | chromadb 1.x Rust 后端对非 ASCII 绝对路径有 bug（索引文件写不出，库静默损坏） |
| 服务器依赖不锁版本 + CPU 版 torch | 本机冻结版本（py3.13）在服务器 py3.10 装不上；Linux PyPI torch 附带数 GB CUDA 包 |

## 5. 经验教训（踩坑全记录）

**数据处理**
1. 出版商水印会嵌入零宽空格（`pubs.​acs.​org`）且被双栏打碎，行级正则清不掉——
   必须"行级过滤 + 合并后模式清除"两级处理（ingest.py `_POST_MERGE_WATERMARKS`）。
2. Science.org 的 PDF 用 U+2003 em 空格而非普通空格，匹配前先统一空白字符（`_ODD_SPACES`）。
3. pymupdf4llm 会把化学式拆成 LaTeX 片段（`Li$_3$MCl$_6$`），破坏精确匹配——评估后未采用（召回 92%<100%）。
4. Crossref 标题嵌 HTML 标签（`Li\n<sub>3</sub>\nYCl`）——citations.py 的 `_clean_meta_text` 专门清理，
   且"数字+空格+元素符号"的空格是标签断口要合并（`Li3 YCl6`→`Li3YCl6`）。

**检索与生成**
5. Python 正则 `\b` 把中文字符当单词字符——中文语境提取化学式必须用 `(?<![A-Za-z0-9])`。
6. 通用 Reranker 偏爱关键词密集文本（数据表），直接覆盖会压制领域排序——精排只能当"投票者"。
7. LLM 参考文献列表会按片段重复列同一文献——生成后按来源去重 + 正文编号重映射 + 相邻编号折叠。
8. 参考文献标题分割正则必须兼容 `**参考文献：**` 等 Markdown 写法。

**工程与环境**
9. chromadb 1.x 中文绝对路径写不出 HNSW 索引（见第 4 节）；判断 DB 是否损坏：新进程 count() 是否报
   `Error loading hnsw index`；修复就是删除重建（前台运行！）。
10. **在 kimi-code 后台任务里跑建库脚本会导致索引文件不完整**（进程组被杀时 flush 中断）——
    建库/评估一律前台跑。
11. 服务器 pip 装机：先装 CPU 版 torch（download.pytorch.org/whl/cpu），再装其余；
    `audioop-lts` 之类 3.13 专属包要加 `; python_version >= "3.13"` 标记。
12. arXiv API 对频繁请求返回 406 软封禁——浏览器 UA + 指数退避（8s/20s）+ 失败保留旧缓存。
13. Gradio 版本差异大（`type` 参数移除、theme/css 移到 launch()、BarPlot 无 vertical、
    auth 是表单登录而非 HTTP Basic）——升级 Gradio 前先在本地全功能验证。
14. Windows 控制台 GBK 乱码只是显示问题；Python 脚本统一 `-X utf8` 或确保文件 UTF-8。
15. **用户会在编辑器里手动改代码**（曾覆盖掉清洗逻辑并引入崩溃）——发现行为异常先 diff 文件，
    并与使用者约定"改动通过对话进行"。

**发布与安全**
16. 申报书含手机号/邮箱，公开仓库前必须移出（已入 .gitignore）；密钥只在 .env，绝不入 git。
17. 公网部署必须有访问口令（防刷 API 额度）+ 上传口令（防无关文件入库）。

## 6. 常用操作手册

**本地开发（Windows, Git Bash）**
```bash
.venv/Scripts/python src/ingest.py          # 重建文本块(pdfs/ 有新文献后)
.venv/Scripts/python src/build_db.py        # 重建向量库(前台! 约3分钟)
.venv/Scripts/python -X utf8 src/evaluate.py  # 跑评估(改检索逻辑后必跑)
.venv/Scripts/python -X utf8 src/qa.py "问题"  # 命令行问答
.venv/Scripts/python app.py                 # 本地网页 http://127.0.0.1:7860
```

**部署到服务器（任何代码改动后）**
用 paramiko/SFTP 同步改动文件到 `/home/ubuntu/hsse/`，然后：
```bash
# 若 chunks.jsonl 变了, 先重建库:
cd /home/ubuntu/hsse && rm -rf data/chroma_db && .venv/bin/python src/build_db.py
sudo systemctl restart hsse-web        # 重启服务
sudo journalctl -u hsse-web -f         # 看日志排错
```
**每次部署后必须做外网验证**（gradio_client 登录 → 问 3 类问题：常规/化学感知/对比）。

**改访问口令**：编辑 `/etc/systemd/system/hsse-web.service` 的
`HSSE_ACCESS_PASSWORD` / `HSSE_UPLOAD_PASSWORD`，然后 `sudo systemctl daemon-reload && sudo systemctl restart hsse-web`。

**arXiv 追踪**：服务器已有 `hsse-arxiv.timer`（每周一 06:30）。手动拉取：
`.venv/bin/python src/arxiv_watch.py --fetch --days 30`。
